# Keys and certificates

**English** | [简体中文](keys.zh-CN.md)

[Project home](../README.md) · [Documentation](README.md)

OTA verification and SSH certificates are used for system updates and login. The materials and procedures for secure boot, disk encryption and OTP/eFuse depend on the board. The relevant examples on this page apply to the currently supported Mixtile Core3588E.

## Prepare for your build

| Build | Required materials |
| --- | --- |
| Complete development image | OTA verification certificate |
| Complete development image and update bundles | OTA signing private key and matching verification certificate |
| Default complete production image | OTA verification certificate, secure boot key set, system encryption key and SSH CA public key |
| Default complete production image and update bundles | The production materials above, plus the OTA signing private key |
| Image generator inputs | OTA verification certificate; production exports also require the SSH CA public key |

If you change the secure boot or encryption switches, the required materials depend on the features actually enabled. The device generates its userdata encryption key on first boot; you do not need to supply it.

## Local directories

Prepare the files in the following default structure. Each directory's README explains how to generate them.

```text
key/
├── ota/
│   ├── signing.cert.pem
│   └── signing.key.pem
├── secure-boot/
│   ├── dev.key
│   ├── dev.crt
│   └── dev.pubkey
├── system-encryption/
│   └── system.key
└── ssh-ca/
    └── ssh_ca_key.pub
```

| Material | Purpose and generation instructions |
| --- | --- |
| `ota/signing.cert.pem` | Installed in the system to verify system and Bootloader update bundles; [OTA README](../key/ota/README) |
| `ota/signing.key.pem` | Signs both types of update bundle and matches the certificate above; required only when generating update bundles |
| `secure-boot/dev.key`, `dev.crt`, `dev.pubkey` | A matching RSA key set for signing RK3588 boot images; [Secure boot README](../key/secure-boot/README) |
| `system-encryption/system.key` | System image encryption key; [System encryption README](../key/system-encryption/README) |
| `ssh-ca/ssh_ca_key.pub` | Public key of the SSH user certificate CA trusted by production devices; [SSH CA README](../key/ssh-ca/README) |

`system.key` must contain **64 lowercase hexadecimal characters**, representing a 32-byte key, with no trailing newline and permissions set to `0600`. It is managed separately from the userdata key generated by the device.

Keep the SSH CA private key and login client private keys on the issuing or administration side; only the CA public key is installed on the device. The certificate's principals must include the actual login username, such as `root` or `naos`.

Do not commit signing private keys or encryption keys to Git. After obtaining the project, generate your own materials as needed or use the materials already associated with your devices. Do not use test keys for production releases.

## Use directories outside the project

You can specify absolute paths through environment variables instead of copying keys into the project:

```bash
export NAOS_OTA_KEY_DIR="$HOME/.local/share/naos-keys/ota"
export NAOS_SECURE_BOOT_KEY_DIR="$HOME/.local/share/naos-keys/secure-boot"
export NAOS_SYSTEM_KEY_DIR="$HOME/.local/share/naos-keys/system-encryption"
export NAOS_SSH_CA_KEY="$HOME/.local/share/naos-keys/ssh-ca/ssh_ca_key.pub"
kas build kas/production.yml
```

The build locates the project root automatically. Use `NAOS_PROJECT_ROOT` only when you need to specify the project location explicitly; normal builds do not require it.

## Generate firmware for existing devices

- **OTA**: Update bundles must be signed with the private key matching the certificate currently trusted by the device. Changing only the build-side private key will cause existing devices to reject installation.
- **Secure boot**: Devices with an OTP/eFuse public-key hash already programmed must use a boot signing key that matches that hash.
- **System encryption**: System update bundles for existing devices must continue to use a `system.key` that the device can unwrap.
- **SSH**: The CA public key in a production image should match the user certificates held by administrators.

Before release, confirm that each set of materials matches its intended use. Do not substitute keys intended for different purposes.

## OTP/eFuse public-key hash

`NAOS_SECURE_BOOT_BURN_KEY_HASH=0` is the default and remains disabled for normal production builds as well.

Set `NAOS_SECURE_BOOT_BURN_KEY_HASH=1` only when you explicitly need the device to program the public-key hash on first boot, and select both the production configuration and secure boot. This option changes the behavior of the generated SPL; it does not program OTP/eFuse on the build host.

**OTP/eFuse programming is irreversible.** Use the default disabled setting for testing. Before programming a device, confirm its state, the signing key and the complete flashing procedure.

## APK repository public key

`NAOS_APK_PUBLIC_KEY` specifies the NAOS APK repository verification public key used by the device. The default is the repository public key supplied with the project; it is not the APK repository signing private key.

For a self-hosted APK repository, configure both its address and the matching verification public key. The APK repository private key is kept by the package builder and repository maintainer; normal system builds do not need it.
